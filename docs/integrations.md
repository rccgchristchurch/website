# Hosting, live content and feedback

What is in the `site/` folder, how to run it, how to publish it, and how the three live pieces work.

## 1. What `site/` is

`site/` is the Claude Design export of the first draft, promoted to the hostable root:

| File | Role |
|---|---|
| `index.html` | The whole prototype (27 screens switched by the PROTOTYPE toolbar at the top). Our edits for YouTube, calendar and feedback live in here. |
| `CCE Header.dc.html`, `CCE Footer.dc.html` | Shared header and footer, loaded by `index.html`. |
| `support.js`, `_ds/` | The Claude Design runtime and design-system stylesheet. Do not edit. |
| `site-config.js` | The only file non-developers touch: YouTube channel, calendar ID, feedback form, social links. |
| `feedback.js` | The floating Feedback button shown on every screen. |
| `data/feeds.json` | Generated by `scripts/fetch-feeds.mjs`. Latest videos, live status, calendar events. |
| `single-page-draft.dc.html` | The earlier one-page draft from the same export, kept for reference. |
| `.nojekyll` | Tells GitHub Pages to serve the `_ds` folder (Jekyll would otherwise drop folders starting with `_`). |
| `assets/logos/` | Logos downloaded from the shared Drive folder on 2026-10-16 and downscaled to 1600px: `church/` (the four New Logo SVGs), `gracepoint/` (adult service), `lighthouse/`, `dc/`, `genesis/`. Precious confirmed on 2026-10-16 that the Gracepoint-folder logo (RCCG seal + "RCCG Christ Church, Edmonton, Act 4 Province 3") is the current church logo, so the header and footer use it; the `church/` SVGs are kept but unused. Lighthouse, Discovery Centre and Genesis pages and cards use their own logos; the Sunday service card also carries the church logo as the adult service. |

The runtime pulls React and Babel from unpkg.com at load time, so the site needs internet access to render. That is fine for a review draft. The production site should be rebuilt as plain HTML/CSS (or a CMS theme) from this prototype; see section 7.

## 2. Run it locally

```bash
cd "D:\Projects\Christ church" && node scripts/fetch-feeds.mjs && python -m http.server 8090 --bind 127.0.0.1 --directory site
```

Then open http://127.0.0.1:8090. The Claude desktop app can also start it from `.claude/launch.json` (configuration `christ-church-site`).

## 3. Publish on GitHub Pages

1. Create a GitHub repository (GitLab works too, but the included workflow is GitHub Actions; GitLab Pages needs a `.gitlab-ci.yml` instead).
2. Push this folder to `main`.
3. Repository settings, Pages, set **Source** to **GitHub Actions**.
4. The workflow in `.github/workflows/deploy-pages.yml` runs on every push, every hour, and on demand. It fetches the feeds, then publishes `site/`.

The hourly schedule is what keeps the latest sermon, live status and calendar current without anyone editing the website.

## 4. YouTube: latest Sunday, latest midweek, live

Channel: RCCG Christ Church Edmonton, ID `UCoqF4wZyvVON6lmCtC2Jzdw` (from the old site's footer, verified 2026-10-15). No API key is used.

How it works:
- `scripts/fetch-feeds.mjs` reads the channel's public RSS feed (last 15 uploads) and the channel's `/live` page, and writes `site/data/feeds.json`.
- Videos are classified by title with the patterns in `site-config.js` (`youtube.classify`). Current channel titles already fit: "Sunday Service | Sun. Oct. 11, 2026", "Midweek Bible Study | Wed. Oct. 14, 2026", "Lighthouse Service | ...".
- Home shows the latest Sunday service. Watch shows the live stream when the church is live, otherwise the latest Sunday service, plus the latest midweek service and a grid of recent uploads filterable by Sunday / Midweek / Lighthouse.
- If `feeds.json` is missing (fresh clone, script not run) the page falls back to an embed of the channel's uploads playlist, which always starts at the newest video.

What the media team must keep doing: title uploads consistently. If the wording changes, update the regex strings in `site-config.js`.

Live stream note: YouTube's `/live` page only reports a broadcast while it is on air. Because the feed refreshes hourly on Pages, the Watch page may lag up to an hour in switching to or from live. The "Watch live on YouTube" button always opens the channel's live page directly, so viewers are never stuck.

## 5. Church calendar

Set-up, once, by the church office:
1. In Google Calendar create a calendar named "Christ Church Edmonton Events".
2. Settings, Access permissions, tick **Make available to public**.
3. Copy the **Calendar ID** (looks like `abc123@group.calendar.google.com`) into `site-config.js` under `calendar.googleCalendarId`.
4. Share edit access with whoever posts events (office, ministry leads).

After that, every event added in Google Calendar:
- appears in the embedded month view on the Events page (immediately, it is a live embed);
- appears as event cards on Home and Events within the hour (from `feeds.json`, which parses the calendar's public ICS feed, next 90 days, including simple weekly repeats);
- is tagged to a ministry automatically when the title mentions Genesis, Discovery, Lighthouse, Men of Impact, Women of Zion, Couples or Seniors.

Members can subscribe to the same calendar on their phones from the "Subscribe on your phone" link.

## 6. Feedback button (HOD review)

A floating **Feedback** button sits bottom-right on every screen. It records which screen and viewport the reviewer was on, their name, department and comment.

Two ways to receive it:
- **Email (works today):** the button opens the reviewer's email client addressed to `info@rccgchristchurch.ca` with everything filled in. Change the address in `site-config.js`.
- **Google Form (recommended for a review round):** create a Google Form with four short-answer questions: Page, Name, Department, Feedback. Open the form's "Get pre-filled link", fill dummy values, copy the link, and read the `entry.NNNNNN` id for each question. Put the form's `formResponse` URL and the four ids into `site-config.js` under `feedback.googleForm`. Submissions then land silently in the form's response sheet, one row per comment, with no email client involved.

Set `feedback.enabled: false` (or remove `feedback.js` from `index.html`) before public launch.

## 7. Database and the road to production

GitHub Pages serves static files only, so "a database" means one of these:

| Need | Simplest fit |
|---|---|
| Events | Google Calendar (already wired) |
| Sermons / videos | YouTube (already wired) |
| Forms: prayer requests, first timers, membership, business directory submissions | Google Forms writing to Google Sheets, or Formspree / Netlify Forms. No server. |
| Editable page content by staff | Decap CMS (free, edits commit to the repo) or a hosted CMS such as WordPress, which the project charter mentions |
| Real database with login, business directory search, member records | Supabase or Firebase free tier, called from the page with a public key. Needs a developer and a privacy review before storing member data. |

Recommended order: keep the static site, add Google Forms for the Connect page forms, add Decap CMS when staff need to edit copy, and only add Supabase if the business directory or membership needs search and accounts.

The prototype runtime (React via unpkg, Claude Design's template language) is right for review but not for launch. When the design is approved, rebuild the approved screens as static HTML/CSS using the CSS tokens on the prototype's Design system screen, keep `site-config.js`, `feedback.js`, `scripts/fetch-feeds.mjs` and the workflow as they are, and the live pieces carry over unchanged.
